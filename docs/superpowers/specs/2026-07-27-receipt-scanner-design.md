# レシート清算スキャナー 設計ドキュメント

作成日: 2026-07-27
ステータス: レビュー中(ユーザー承認済みセクション: アーキテクチャ / 画面フロー / エラー処理・テスト・実装体制)

## 1. 背景と目的

夫婦の月次清算を自動化する。現状は月末に妻が、夫婦それぞれの1ヶ月分のレシートを計算機で手計算し、「今月は夫が◯◯円、妻が◯◯円払った」を算出している(家賃等は夫がまとめて支払っており、その調整も手計算)。

このアプリは、スマホカメラで撮ったレシートをまとめて読み取り、計算機なしで両者の支払合計と差額を出せるようにする。

## 2. 要件(確定事項)

- **利用者**: 妻が1人、自分のスマホのブラウザで使用(単一デバイス完結)
- **利用頻度**: 月末のみ
- **読取項目**: 各レシートの**合計金額のみ**(店名・日付・品目は不要)
- **清算ロジック**: 夫グループ/妻グループそれぞれの合計と差額を表示できれば十分。家賃などレシートのない支出は手動追加行で対応
- **インフラ**: DBなし、サーバーなし、完全無料で運用、無料ホスティングにデプロイ
- **OCR**: 無料・高精度・オープンソース(Gemini等の商用APIは使わない)

## 3. 技術調査の結論(2026-07 実施)

3並列のWeb調査(クラシカルOCR / オープンVLM / ホスティング・既存アプリ)の要点:

1. **PaddleOCR系がOSS日本語OCRの精度最高クラス**。2025年以降、公式ブラウザSDK(`@paddleocr/paddleocr-js`)と、MITライセンスの `ppu-paddle-ocr`(PP-OCRv6 tinyモデル約6MB、日本語含む50+言語、WebGPU対応・WASMフォールバック)が登場し、ブラウザ内OCRが実用段階。レシートで文字精度99.2%の報告あり
2. **Tesseract.js は日本語レシートで精度不足**(CER 0.346)。EasyOCRはCPUで遅すぎ、docTRは日本語モデルなし
3. **VLM系(PaddleOCR-VL等)は精度が高いがGPU/ローカルMac前提**で、無料Webサービスへの常時デプロイ手段がない
4. **無料サーバーは2026年時点でほぼ消滅**(Railway/Fly.io廃止、HF Spacesの無料Gradio/Docker制限、Renderのみ残存だがコールドスタート約1分)。月末のみ使用のアプリと相性が悪い
5. **静的ホスティングは健在**: GitHub Pages(帯域100GB/月ソフトリミット)、Cloudflare Pages(帯域無制限)。常時HTTPSでカメラ要件を満たす
6. どのOCRでも**誤読前提の手動修正UIが必須**(実運用記事の共通結論)
7. 既存OSSに日本語レシート対応の完成品Webアプリはない

採用方式: **完全ブラウザ内OCR(方式A)**。理由: 無料・DBなし・月末のみ使用の要件に最適(サーバーゼロ、維持費ゼロ、放置しても停止しない)。レシート画像が端末外に出ないためプライバシー面でも有利。「合計金額のみ」の読取なので、数字+キーワード認識ができれば十分であり、モバイル向け軽量モデルでも要求精度を満たせる見込み。

## 4. アーキテクチャ

サーバーもDBも持たない完全クライアントサイドの静的SPA。画像取り込み → 前処理 → OCR → 金額抽出 → 一覧編集 → 集計 の全処理がスマホブラウザ内で完結する。

- **フレームワーク**: Vite + TypeScript + React
- **OCRエンジン**: `ppu-paddle-ocr`(MIT)を第一候補。実装初期に実物レシートで精度検証し、不足なら公式 `@paddleocr/paddleocr-js`(PP-OCRv5)へ切替。**この検証スパイクを最初のマイルストーンとする**
- **デプロイ**: GitHub Pages + GitHub Actions 自動デプロイ(publicリポジトリ。コードのみでレシートデータは一切含まれないため問題なし。private化したい場合はCloudflare Pagesへ移行可能)
- **データ保持**: 作業中データはlocalStorageに自動保存(リロード対策)。「新しい月を始める」でクリア。外部送信なし

## 5. 画面フローとコンポーネント

1画面構成、上から順に:

### 5.1 画像取り込み
- 「アルバムから選ぶ」: 事前に撮り溜めた写真を複数選択(**推奨メインフロー**。`<input type="file" accept="image/*" multiple>`)
- 「カメラで撮る」: アプリ内から1枚ずつ連続撮影(`capture="environment"`、補助フロー)
- 画面上部の「夫/妻」トグルで、取り込み先グループを選択

### 5.2 OCR処理
- 取り込み後、自動で1枚ずつ処理。進捗表示(「3/12枚 処理中…」)
- 前処理: リサイズ+コントラスト補正(感熱紙のかすれ対策として調査で有効性確認済み)

### 5.3 レシート一覧
- 1レシート=1行: サムネイル / 金額(タップで手動修正) / 夫⇄妻の移動 / 削除
- 抽出に自信がない場合(キーワード不検出等)は黄色ハイライトで確認を促す

### 5.4 手動追加行
- レシートのない支出(家賃・光熱費等)を「名前+金額+誰が払ったか」で手入力追加

### 5.5 集計パネル(画面下部固定)
- 夫の合計 / 妻の合計 / 差額をリアルタイム表示
- 「結果をコピー」: 清算サマリーをテキスト化してクリップボードへ(LINE共有用)

## 6. 合計金額抽出ロジック(アプリの頭脳部分)

- OCR結果の全テキスト行から「合計」「お買上げ計」「総計」「お会計」等のキーワード行を探し、同一行(または直近行)の金額を採用
- 「小計」「お預り」「お釣り」「税」行は除外(お預り金額 > 合計金額の罠に注意)
- ¥記号・カンマ・全角数字の正規化
- キーワード不検出時は候補金額を提示しつつ「要確認」フラグ
- このロジックはユニットテストを厚めに書く(§8)

## 7. エラー処理

| 事象 | 対応 |
|---|---|
| OCR失敗(1枚単位) | 金額空欄でリストに載せ手動入力を促す。他画像の処理は継続 |
| モデルDL失敗(初回約6MB) | リトライボタン。成功後はブラウザキャッシュでオフライン動作可 |
| WebGPU非対応端末 | ライブラリの自動WASMフォールバック |
| iOS PWAのカメラ権限不安定問題 | メインフローを「アルバム複数選択」にして権限問題自体を回避 |
| localStorage容量超過 | 保存はサムネイル縮小版のみ。原寸画像は保持しない |

## 8. テスト戦略

- **金額抽出ロジック**: Vitestユニットテスト。実レシートのOCRテキストをフィクスチャ化し、小計/お預りの罠・全角数字・¥/カンマ等を網羅
- **OCR精度検証スパイク**: UI実装前に実物の日本語レシート数枚で `ppu-paddle-ocr` を検証。不足なら公式SDKへ切替判断
- **実機確認**: 完成前に妻のスマホ実機で動作確認(=本番環境)

## 9. 実装体制

- **Fable 5(このセッション)**: 設計・実装計画・各フェーズの受け入れ判断・Codexレビュー指摘の検証と仲裁
- **Sonnet 5**: サブエージェントとして実装担当(フェーズごとに起動)
- **Codex**: 各フェーズ完了時に `codex exec --full-auto --sandbox read-only` でレビュー。指摘はFable 5が検証し、妥当なもののみ反映

## 10. リスクと対策

| リスク | 対策 |
|---|---|
| ppu-paddle-ocr の実レシート精度が期待未満 | 最初のマイルストーンで検証。公式paddleocr-js切替、それでも不足なら方式再検討(iOSショートカット連携等) |
| モバイルモデル特有の誤認識(中国語字形混入等) | 読取対象が数字+少数キーワードのため影響は限定的。文字正規化+手動修正UIでカバー |
| 低スペック端末での処理速度 | WASM時は数秒/枚の想定。進捗表示で体感を緩和。月末のみの利用なので許容範囲 |
| 初回モデルDL(約6MB)の通信 | 初回のみ。以降キャッシュ |
