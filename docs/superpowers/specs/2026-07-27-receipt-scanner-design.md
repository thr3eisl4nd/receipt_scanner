# レシート清算スキャナー 設計ドキュメント

作成日: 2026-07-27
改訂: 2026-07-27 Codexレビュー(条件付き承認)の指摘を検証のうえ反映
ステータス: ユーザーレビュー待ち

## 1. 背景と目的

夫婦の月次清算を自動化する。現状は月末に妻が、夫婦それぞれの1ヶ月分のレシートを計算機で手計算し、「今月は夫が◯◯円、妻が◯◯円払った」を算出している(家賃等は夫がまとめて支払っており、その調整も手計算)。

このアプリは、スマホカメラで撮ったレシートをまとめて読み取り、計算機なしで両者の支払合計と清算額を出せるようにする。

## 2. 要件(確定事項)

- **利用者**: 妻が1人、自分のスマホのブラウザで使用(単一デバイス完結)
- **利用頻度**: 月末のみ
- **読取項目**: 各レシートの**合計金額のみ**(店名・日付・品目は不要)
- **清算ロジック**: 夫グループ/妻グループそれぞれの合計・差額・折半時の清算額を表示。家賃などレシートのない支出は手動追加行で対応
- **インフラ**: DBなし、サーバーなし、完全無料で運用、無料ホスティングにデプロイ
- **OCR**: 無料・高精度・オープンソース(Gemini等の商用APIは使わない)

## 3. 技術調査の結論(2026-07 実施)

3並列のWeb調査(クラシカルOCR / オープンVLM / ホスティング・既存アプリ)の要点:

1. **PaddleOCR系がOSS日本語OCRの精度最高クラス**。2025年以降、公式ブラウザSDK(`@paddleocr/paddleocr-js`)と、MITライセンスの `ppu-paddle-ocr`(PP-OCRv6 tinyモデル約6MB、日本語含む50+言語、WebGPU対応・WASMフォールバック)が登場し、ブラウザ内OCRが実用段階
2. **Tesseract.js は日本語レシートで精度不足**(CER 0.346)。EasyOCRはCPUで遅すぎ、docTRは日本語モデルなし
3. **VLM系(PaddleOCR-VL等)は精度が高いがGPU/ローカルMac前提**で、無料Webサービスへの常時デプロイ手段がない
4. **無料サーバーは2026年時点でほぼ消滅**(Railway/Fly.io廃止、HF Spacesの無料Gradio/Docker制限、Renderのみ残存だがコールドスタート約1分)。月末のみ使用のアプリと相性が悪い
5. **静的ホスティングは健在**: GitHub Pages(帯域100GB/月ソフトリミット)、Cloudflare Pages(帯域無制限、`_headers`でカスタムヘッダー設定可)。常時HTTPSでカメラ要件を満たす
6. どのOCRでも**誤読前提の手動修正UIが必須**(実運用記事の共通結論)
7. 既存OSSに日本語レシート対応の完成品Webアプリはない

採用方式: **完全ブラウザ内OCR(方式A)**。理由: 無料・DBなし・月末のみ使用の要件に最適(サーバーゼロ、維持費ゼロ、放置しても停止しない)。レシート画像が端末外に出ないためプライバシー面でも有利。「合計金額のみ」の読取なので、数字+キーワード認識ができれば十分であり、モバイル向け軽量モデルでも要求精度を満たせる見込み。

### 3.1 OCRエンジンの位置づけ(Codexレビュー反映)

`ppu-paddle-ocr` は**検証中候補**とする(「第一候補」に格上げするのは実機検証後)。理由:

- 公開ベンチマーク(レシート文字精度99.2%)は**M1/Bun上の1枚のレシート画像**での数字であり、ターゲット環境(妻のスマホのブラウザ)の実測ではない
- ブラウザ版はcanvas-native実装(OpenCV.js非同梱)
- WebGPUの対応ブラウザにiOS Safariが含まれず、**iPhoneではWASMフォールバック前提**
- マルチスレッドWASMにはCOOP/COEPヘッダー(cross-origin isolation)が必要で、GitHub Pagesはカスタムヘッダー非対応 → 基本シングルスレッド動作

対応方針:

- **検証スパイクを最初のマイルストーンとする**(§8.2 に合否基準)
- OCRエンジンは薄いインターフェースで抽象化し、`ppu-paddle-ocr` と公式 `@paddleocr/paddleocr-js` を差し替え比較できるようにする:

```ts
export type OcrLine = {
  text: string;
  confidence: number;
  box: { x: number; y: number; width: number; height: number };
};

export interface OcrEngine {
  initialize(): Promise<void>;
  recognize(image: HTMLCanvasElement): Promise<OcrLine[]>;
  destroy(): Promise<void>;
}
```

- ライブラリと `onnxruntime-web` は**完全固定バージョン**。モデル・辞書・WASMは**自サイトに同梱**(デフォルトのリモート取得を使わない)。外部CDN・外部フォント・分析タグなし
- オフライン動作は要件外とし、保証しない(Service Workerは導入しない)

## 4. アーキテクチャ

サーバーもDBも持たない完全クライアントサイドの静的SPA。画像取り込み → 前処理 → OCR → 金額抽出 → 一覧編集 → 集計 の全処理がスマホブラウザ内で完結する。

- **フレームワーク**: Vite + TypeScript + React(ルーター・グローバル状態管理ライブラリは使わない)
- **OCRエンジン**: §3.1 の通り検証スパイクで決定
- **デプロイ**: GitHub Pages + GitHub Actions 自動デプロイ(publicリポジトリ。コードのみでレシートデータは一切含まれないため問題なし)。スパイクでシングルスレッドWASMが遅すぎる場合は Cloudflare Pages へ移行し `_headers` で COOP/COEP を設定してマルチスレッド化する
- **データ保持**: 作業中データ(金額・支払者・状態のみ)はlocalStorageに自動保存。「新しい月を始める」でクリア。外部送信なし(§7)

## 5. 画面フローとコンポーネント

1画面構成、上から順に:

### 5.1 画像取り込み
- **「夫のレシートを追加」「妻のレシートを追加」の2ボタン**(トグル方式は取り違えやすいため不採用)
- 各ボタンから: アルバム複数選択(**推奨メインフロー**、`<input type="file" accept="image/*" multiple>`)または カメラ1枚撮影(`capture="environment"`、補助フロー)
- ファイル選択直後に空行を作成して保存し、OCR結果で後から更新する(処理中もリストに存在が見える)
- 同一ファイル(名前+サイズ+lastModified一致)の再追加は警告
- 処理後にfile inputの `value` をクリアし、同じファイルを再選択可能にする

### 5.2 OCR処理
- 取り込み後、自動で**1枚ずつ直列処理**(並列OCR禁止。iPhoneの高解像度画像はデコード時メモリが問題になるため)。処理後に `URL.revokeObjectURL()`・一時Canvas解放・画像参照破棄
- ステータスを分離して表示: 「モデル準備中」/「画像 3/12 処理中」/「金額確認待ち N件」
- 前処理は二段階: まず回転補正+リサイズのみでOCR → 失敗・低信頼時のみコントラスト補正版で再試行(全画像への強い補正は薄い数字を消すリスクがあるため)
- 一括キャンセル、失敗行のみ再試行、手入力への切り替えを用意

### 5.3 レシート一覧
- 1レシート=1行: サムネイル(タップで拡大) / 金額(タップで修正、`inputMode="numeric"`、編集中はカンマなし・確定後カンマ表示) / 夫⇄妻の移動 / 削除
- 各行に確認状態を持つ(色+テキストで表示。色だけに頼らない):

```ts
type VerificationStatus =
  | "auto-high"     // キーワード一致・高信頼で自動確定
  | "needs-review"  // 候補はあるが要確認
  | "confirmed"     // ユーザーが確認済み
  | "manual"        // 手入力
  | "failed";       // OCR失敗(金額空欄)
```

### 5.4 手動追加行
- レシートのない支出(家賃・光熱費等)を「名前+金額+誰が払ったか」で手入力追加

### 5.5 集計パネル(画面下部固定)
- 夫の合計 / 妻の合計 / 差額 / **折半時の清算額(差額÷2)と支払方向**(「妻 → 夫 ◯◯円」)を表示
- 「結果をコピー」: 清算サマリーをテキスト化してクリップボードへ(LINE共有用)。`needs-review` / `failed` が残っている場合は「未確認 N件」と警告
- ソフトキーボード・最終行を隠さないよう下パディングと `env(safe-area-inset-bottom)` を確保

## 6. 清算・金額のルール

- 金額は**円単位の整数**で保持する
- 全行を50:50の共有支出として扱う。清算額 = |夫合計 − 妻合計| ÷ 2(端数は切り捨て。1円の端数は多く払った側が負担)
- 返品・取消(`▲1,280` / `-1,280`)は負の金額として扱える
- 個人支出の除外・折半以外の負担率はv1対象外

```ts
function settle(husbandYen: number, wifeYen: number) {
  const deltaYen = husbandYen - wifeYen;
  const transferYen = Math.floor(Math.abs(deltaYen) / 2);
  const direction =
    deltaYen > 0 ? "妻 → 夫" : deltaYen < 0 ? "夫 → 妻" : "清算なし";
  return { totalYen: husbandYen + wifeYen, deltaYen, transferYen, direction };
}
```

## 7. 金額抽出ロジック(アプリの頭脳部分)

OCR結果は**テキストだけでなくバウンディングボックスを保持**し、空間的位置で「キーワード ↔ 金額」を結び付ける(OCRの読み順はレシートの視覚配置と一致しない場合があるため、「同一行または直近行」の文字列近接だけでは不十分)。

### 7.1 キーワード

正候補(加点): 合計 / 税込合計 / 総合計 / お買上げ計 / お買上金額 / お会計 / ご請求額 / ご請求金額 / 今回お支払額 / 現計

除外・大幅減点: 小計 / 8%対象 / 10%対象 / 課税対象 / 消費税 / 内税 / 外税 / 税額 / お預り / お釣り / 釣銭 / 現金 / クレジット / 電子マネー / ポイント / 残高 / 値引 / 割引額 / 商品点数 / 電話番号 / 伝票番号

### 7.2 正規化

NFKC正規化(全角→半角)、`O/o→0`・`I/l→1` 等の数字誤認補正、`¥ ￥ 円 , 空白 ー` の除去、`▲` → 負号。整数チェックと上限(1,000万円)チェック。

### 7.3 候補スコアリング

- 強キーワードと同一行(box座標のY重なり): 加点
- キーワードの右側 or 1〜2行下: 加点
- レシート下半分: 小さく加点
- `¥ ￥ 円` 付き: 加点
- OCR confidence: 加点
- 除外語付近: 大幅減点

判定: 最高スコア候補が明確 → `auto-high`。候補が拮抗・複数 → `needs-review`(上位2〜3候補を提示)。候補なし → `failed`(空欄で手入力へ)。**金額最大値のフォールバック採用はしない**(お預り金額 > 合計金額の罠)。

### 7.4 想定エッジケース(テストフィクスチャ化する)

- 8%・10%の税率別金額が並ぶレシート
- クーポン・ポイント利用で複数の「合計」がある
- レシートとカード利用票が同じ写真に写っている
- 返品・取消の負の金額
- `￥１，２３４－` などの全角・記号混じり
- 長いレシートの下部が切れて合計が写っていない
- 同一レシートの二重登録

## 8. データ保持(localStorage)

- 保存するのは**金額・支払者・確認状態・名前・対象月のみ**(円整数)。**画像・サムネイルはlocalStorageに入れない**(約5MiB制限+Base64で33%増のため)。サムネイルはv1ではメモリ上のみ(リロードで消えるのは許容)
- localStorageは「同一作業中のクラッシュ・リロード復旧用」であり、バックアップではない
- スキーマはバージョン付き。JSON破損・旧スキーマは検証して安全に破棄
- 保存失敗(容量超過等)は黙殺せず「自動保存できません」を表示
- 「新しい月を始める」は対象月と現在の合計を表示して確認ダイアログを挟む

```ts
const STORAGE_KEY = "receipt-scanner:state:v1";

type PersistedState = {
  version: 1;
  month: string; // "2026-07"
  updatedAt: string;
  rows: Array<{
    id: string;
    payer: "husband" | "wife";
    amountYen: number | null;
    label: string;
    status: VerificationStatus;
    source: "ocr" | "manual";
  }>;
};
```

## 9. エラー処理

| 事象 | 対応 |
|---|---|
| OCR失敗(1枚単位) | `failed` 行として残し手動入力を促す。他画像の処理は継続 |
| 画像デコード失敗・未対応形式・巨大画像 | OCR失敗とは区別したメッセージを表示 |
| モデルDL失敗(初回約6MB、自サイト同梱) | リトライボタン |
| WebGPU非対応端末(iPhone想定) | WASMフォールバック(自動) |
| iOS PWAのカメラ権限不安定問題 | メインフローを「アルバム複数選択」にして権限問題自体を回避。PWA化はしない |
| localStorage保存失敗 | 「自動保存できません」表示(黙殺しない) |

アクセシビリティ: 進捗は `aria-live`、エラーは `role="alert"`。状態は色+テキストで表現。

## 10. テスト戦略

### 10.1 金額抽出ロジック
Vitestユニットテスト。実レシートのOCR結果(box座標付き)をフィクスチャ化し、§7.4のエッジケースを網羅。

### 10.2 OCR実機検証スパイク(最初のマイルストーン)
UI実装前に、過去2〜3ヶ月分から店舗・撮影条件の異なる実物レシート(目標30枚以上)で `ppu-paddle-ocr` を検証。測るのは文字認識率ではなく:

- 合計金額の完全一致率 / 誤金額を自動確定した件数 / 手修正が必要だった件数
- 初回ロード時間 / 1枚あたりp50・p95処理時間 / 20〜30枚連続処理でのクラッシュ有無

暫定合格基準:

```text
- 合計金額の完全一致率: 90%以上
- 自動確定(auto-high)の誤り: 検証データ上0件
- WASM時p95: 10秒/枚以下
- 30枚連続処理でタブクラッシュなし
- 失敗画像はすべて手入力へ復旧可能
```

不合格なら: 公式 `@paddleocr/paddleocr-js` へ切替(§3.1の抽象化で差し替え可能) → それでも不足なら方式再検討(iOSショートカット連携等)。

### 10.3 実機確認
完成前に妻のスマホ実機(=本番環境)で、実際の月末フロー(30枚前後の連続処理、バックグラウンド移行・画面ロック復帰含む)を確認。

## 11. スコープ外(YAGNI)

v1では実装しない: ルーター / グローバル状態管理ライブラリ / 認証 / 履歴保存・DB / クラウド同期 / 高度な傾き自動補正 / 画像ハッシュによる重複検出 / 自前のWeb Worker実装(ライブラリ組込のオプションがあれば利用可) / PWA・オフライン対応 / JSON・CSVエクスポート

## 12. 実装体制

- **Fable 5(このセッション)**: 設計・実装計画・各フェーズの受け入れ判断・Codexレビュー指摘の検証と仲裁
- **Sonnet 5**: サブエージェントとして実装担当(フェーズごとに起動)
- **Codex**: 各フェーズ完了時に `codex exec --sandbox read-only` でレビュー。指摘はFable 5が検証し、妥当なもののみ反映

## 13. リスクと対策

| リスク | 対策 |
|---|---|
| ppu-paddle-ocr の実機精度・速度が合格基準未達 | §10.2のスパイクで早期判定。公式SDK切替 → 方式再検討の順でフォールバック |
| モバイルモデル特有の誤認識(中国語字形混入等) | 読取対象が数字+少数キーワードのため影響は限定的。正規化+確認状態+手動修正UIでカバー |
| iPhoneでシングルスレッドWASMが遅い | 進捗表示で体感緩和。不足ならCloudflare Pages+COOP/COEPでマルチスレッド化 |
| 初回モデルDL(約6MB、自サイト同梱) | 初回のみ。以降ブラウザHTTPキャッシュ |
